01

Security

The one finding that needs same-day attention is here. The rest of the platform's security posture is more solid than it looks at first pass — see what's already solid below for what I checked and ruled out.

Critical

Any WhatsApp media file, from any tenant, is downloadable without logging in

GET /media/whatsapp/:messageId has no auth middleware at all, and messageId is a plain sequential integer (messages.id AUTO_INCREMENT). Anyone — no account, no token — can request id=1, id=2, id=3… and stream back the image, voice note, video or document attached to that message, for any conversation, in any agency, on the whole platform. This is the only finding in the report that's a live, walk-up-and-exploit data leak rather than a weakness that needs a specific trigger.

Evidence
chatbot_api/routes/media.js:13
router.get("/media/whatsapp/:messageId", async (req, res) => {
  const { messageId } = req.params;
  const [rows] = await pool.query("SELECT media_url FROM messages WHERE id = ?", [messageId]);
  // no authMiddleware, no agency_id / ownership check anywhere in this file
ImpactCross-tenant confidentiality breach — customer photos, ID documents, voice notes and files sent through any connected WhatsApp number are exposed to an unauthenticated, unrelated party.
Fix shapeAdd authMiddleware, then join through to the message's conversation and check conversation.agency_id === req.user.agencyId before streaming — the same ownership-check shape already used in routes/conversations.js.
High

Inbound Meta/Telegram webhooks are never signature-verified

The GET handshake that Meta performs once to register a webhook URL is checked (hub.verify_token), but the actual POST deliveries — every inbound message, delivery status, read receipt and call event, for every connected number on the platform — are accepted with no X-Hub-Signature-256 HMAC check. Anyone who learns the webhook URL can POST a forged payload: fake inbound messages that get run through bot flows, fake "delivered/read" statuses on broadcasts, fake call events. Meta's own docs treat this signature check as mandatory for exactly this reason.

Evidence
chatbot_api/routes/webhook.js — grep for "signature" or "hmac": no matches.
Contrast chatbot_api/routes/billing.js:122, which does it correctly:
  const sig = req.headers["stripe-signature"];
  stripe.webhooks.constructEvent(req.rawBody, sig, endpointSecret);
ImpactForged inbound traffic can trigger bot flows, pollute conversation history, or falsify broadcast delivery analytics — without ever touching a real WhatsApp/Messenger/Telegram account.
Fix shapeThe pattern already exists in this codebase (billing.js) — port it: compute HMAC-SHA256 of the raw body with the app secret, compare to X-Hub-Signature-256, reject on mismatch, before any payload processing.
High

No rate limiting anywhere — including login

There's no express-rate-limit, no slow-down middleware, no attempt counter, on any route in the API — confirmed by searching the whole backend and package.json. POST /auth/login in particular can be hit as fast as the network allows, with no lockout, no backoff, no CAPTCHA — a scripted password-guessing run against any known email address is unthrottled.

ImpactCredential-stuffing / brute-force risk on every account, plus the API in general has no defense against scripted abuse or accidental hammering.
Fix shapeexpress-rate-limit on /auth/login and /auth/register first (tight — a handful of attempts per IP per minute), then a looser global limit on the rest of /api/v1.
High

Three actively-used dependencies have known, patched vulnerabilities

Confirmed live with npm audit on both projects — this isn't advisory noise from dev-only tooling, these three are in the runtime path of every request.

Evidence — npm audit --omit=dev
chatbot_api  mysql2 <=3.23.0 — auth-plugin downgrade leaks plaintext DB credentials;
             unbounded zlib inflate allows a decompression-bomb DoS
chatbot_ui   axios (direct dep, services/api.js) — in the vulnerable 1.0.0–1.17.0
             range; ~29 advisories incl. SSRF via NO_PROXY bypass, prototype
             pollution → auth bypass / request hijacking
chatbot_ui   react-router (direct dep, 6.0.0–7.17.0) — open redirect, stored XSS
             in SSR redirect handling, unauthenticated DoS via route matching

Separately, jspdf shows two critical-severity CVEs, but a full source search found zero call sites — it's an installed, unused dependency. Real severity today is low, but it should be upgraded or removed before anyone wires it up.

Impactmysql2 is the entire app's DB layer; axios is every frontend API call; react-router is the entire routing tree — patched versions exist for all three today.
Fix shapenpm audit fix for mysql2 (non-breaking); axios and react-router need a version bump + a quick regression pass since both are wired everywhere.
Medium

Dev-tunnel domains are trusted by CORS even in production

The CORS origin check allowlists *.ngrok-free.dev, *.ngrok.io, *.ngrok-free.app and *.loca.lt unconditionally, with credentials: true — this branch runs whether or not NODE_ENV === 'production'. Only the final "allow anything unmatched" fallback is gated to non-production. Anyone can spin up a free ngrok tunnel in seconds; if this code is what's actually deployed, a page hosted on that tunnel's origin can make credentialed requests against the live API.

Evidence
chatbot_api/index.js:109
if (allowed.includes(origin) ||
    origin.endsWith('.loca.lt') || origin.endsWith('.ngrok-free.dev') ||
    origin.endsWith('.ngrok.io') || origin.endsWith('.ngrok-free.app')) {
  return callback(null, true);           // ← not gated by NODE_ENV
}
if (process.env.NODE_ENV !== 'production') return callback(null, true);
return callback(new Error('Not allowed by CORS'));   // only this line is gated
ImpactNarrower than it looks — needs a live tunnel URL, not a walk-up exploit — but it's a real, avoidable crack in an otherwise properly-allowlisted production CORS policy.
Fix shapeWrap the tunnel-domain branch in the same NODE_ENV !== 'production' check the fallback already uses.
Low · Info

102 unaudited console.log calls in the API

Not a vulnerability by itself, but worth a pass: some of these log full request bodies or webhook payloads, which in a production log aggregator can mean tokens, phone numbers or message content sitting in plaintext logs. No structured logger or log-level control exists — everything ships to stdout the same way in every environment.

Fix shapeA short grep-and-review pass, then consider a minimal logger (pino/winston) with levels, so debug noise can be turned off in production without deleting it.
02

Correctness & Reliability

Two of these are the same root-cause bug already found and fixed twice earlier this build (WhatsApp Calling, then Broadcasting) — it turns out it wasn't fully stamped out.

High

The old Campaigns system still picks "the first active integration" — same bug as before, still live

routes/campaigns.js and utils/campaignRunner.js are superseded by this build's new Broadcasting module, but they're still mounted in index.js and still reachable at POST /api/v1/campaigns. The runner picks an integration with an unordered LIMIT 1 — the exact anti-pattern already diagnosed and fixed twice this session (WhatsApp Calling picking a dead number; the new Broadcasting sending from the wrong number). Nothing in the current UI calls this endpoint anymore (campaignAPI is defined in services/api.js but referenced from zero pages) — it's dead from the dashboard's point of view, but not dead on the server.

Evidence
chatbot_api/utils/campaignRunner.js:32
"SELECT * FROM integrations WHERE agency_id = ? AND platform = ? AND is_active = 1 LIMIT 1"
ImpactAny agency with two integrations on the same platform gets silently wrong-number sends if this endpoint is ever hit — directly, by an old bookmark, or by anything external still pointed at it.
Fix shapeEither retire the route entirely (nothing in the UI uses it), or port the same explicit-integration_id fix already applied to Broadcasting.
Medium

Follow-up Sequences has the same "first active integration" fallback

Unlike the dead Campaigns route above, Sequences is a live, current feature. When a sequence step fires for a contact with no prior message history to infer the right number from, it falls back to the same unordered pick — the code comment even names the ambiguity it's guessing around.

Evidence
chatbot_api/utils/sequenceRunner.js:258
// the API with no prior contact) — fall back to any active integration,
// same as before, since there's no "which one did they actually use" to go on.
:261  "SELECT * FROM integrations WHERE agency_id = ? AND platform = ? AND is_active = 1 LIMIT 1"
ImpactAn agency running Sequences with two numbers on the same platform can have step messages silently sent from the wrong one — same symptom as the two bugs already fixed this session.
Fix shapeSame pattern already proven twice: an explicit, required integration choice at sequence-creation time, falling back automatically only when exactly one candidate exists.
Medium

Zero automated tests in the entire project

No *.test.js/*.spec.js file exists anywhere in either project. chatbot_api's own npm test is still the unedited scaffold placeholder that exits with an error. Every fix made during this build was verified by hand — minting a real JWT, hitting the real API, checking the DB — which is solid discipline, but it means there's no safety net catching a regression the next time something nearby changes.

Evidence
chatbot_api/package.json  "test": "echo \"Error: no test specified\" && exit 1"
Fix shapeDoesn't need to start big — a thin layer over the riskiest paths (login, message send, webhook intake, the two integration-selection bugs above) would already catch the regressions most likely to actually happen.
Low

The blog feature fails one of its table-init checks on every single boot

Printed on every backend start this session, silently swallowed: MySQL doesn't allow a default value on a TEXT/BLOB/JSON column, and the blog table's tags column is defined with one.

Evidence — real backend startup log, this session
❌ Blog table init error: BLOB, TEXT, GEOMETRY or JSON column 'tags' can't have a default value
Fix shapeDrop the default on that column, or switch it to a type that allows one — small, contained schema fix.
03

Architecture & Code Health

Nothing here is urgent. All of it gets more expensive to fix the longer the project keeps growing at its current pace.

Medium

Several superseded systems are still live side-by-side with their replacements

Beyond the Campaigns/Broadcasting overlap above: fb_comment_rules and its UI in FacebookPage.jsx are dead — never read by the live comment-automation path in webhook.js. comment_automation_rules.private_reply_buttons is a column nothing reads or writes. None of these are actively harmful, but each one is a trap for a future change made in the wrong copy of the logic.

Fix shapeA deliberate deprecation pass — confirm dead, remove the route/column/UI together rather than leaving the fork.
Medium

36 migration scripts, no record of which ran where

Every schema change in this project is its own standalone migrate_*.js file, run by hand. Each one is individually idempotent (existence-checked), which is good practice — but there's no table recording which of the 36 have actually been applied to a given environment, so a fresh deploy has no way to know it ran all of them, in order, short of running every single one and reading the console output.

Fix shapeA minimal schema_migrations(name, applied_at) ledger and a tiny runner that skips what's already recorded — doesn't require touching any of the 36 existing scripts' logic.
Medium

The entire dashboard ships as one 2.88 MB JavaScript file

Confirmed repeatedly by this session's own production builds — one bundle, no route-based code splitting. A user logging in as a Live Chat Agent downloads the full Flow Builder (10,647 lines on its own), every Super Admin screen, every channel's settings page, and everything else, before they see the inbox.

Evidence — this session's own vite build output
dist/assets/index-*.js   2,886.60 kB │ gzip: 755.08 kB
(!) Some chunks are larger than 500 kB after minification.
Fix shapeReact.lazy + dynamic import() per top-level route, starting with Flow Builder and the Super Admin section — the two biggest, least-often-needed-on-first-load chunks.
Low

A handful of single-file components are getting hard to safely change

FlowBuilderPage.jsx (10,647 lines), InboxPage.jsx (4,387), WhatsAppTemplateManager.jsx (2,923), BotManagerPage.jsx (2,761) — all still workable today, all edited successfully multiple times this session, but each one is a single component doing the work of what would elsewhere be ten.

Fix shapeNot urgent — worth a planned decomposition pass per file when one of them is next touched for a feature, rather than a dedicated refactor sprint.
Low

Neither project ships a .env.example

.env itself is correctly gitignored in both projects (see Already Solid) — but with no example file, setting up a new environment means reverse-engineering every required variable name from process.env.* references in source.

Fix shapeA committed .env.example with every key referenced in source, values blanked — five-minute fix, meaningful onboarding win.
04

What's Already Solid

Checked and ruled out, not assumed — worth stating plainly so the findings above read against an accurate baseline.

  • ✓No SQL injection found. Every place a column or table name is built dynamically (routes like admin.js, agencyPackages.js, sequences.js) constructs it from fixed string literals, never from request input — values always go through parameterized ? placeholders.
  • ✓.env is correctly gitignored in both projects, and a full source scan found no hardcoded secrets, API keys or passwords anywhere in the codebase.
  • ✓The Stripe billing webhook verifies its signature correctly (routes/billing.js:122) — proof the pattern the Meta webhook finding above is missing is already known and used elsewhere in this exact codebase.
  • ✓Production CORS is a real allowlist, not a wildcard — the one gap is the narrower dev-tunnel issue above, not the policy as a whole.
  • ✓helmet is active for baseline HTTP security headers, and file uploads (routes/upload.js) already validate type and size before accepting anything.
  • ✓JWT_SECRET has no insecure fallback — an unset secret makes every token operation fail loudly, rather than silently signing with something guessable.
  • ✓The multi-tenant permission system is real and consistently used — Platform → Reseller → Reseller's End User, enforced through one actual organization_members/roles/role_permissions system rather than scattered role checks. The Support Desk built earlier this session slotted into it cleanly, which is a good sign for the design.
05

New Feature Ideas

Grounded in what's already built, not generic suggestions — each one either completes something left deliberately half-finished this session, or fills a gap the audit above surfaced directly.

Support Desk

Email notifications for tickets

Scoped out when the Support Desk was built this session — no SMTP layer exists anywhere in the API yet. New-ticket and new-reply emails are the natural next step.

Support Desk

CSAT trend reporting

Every solved ticket already captures a 1–5 rating. Nothing aggregates it into a trend line per agency or per agent — a small addition on top of data already being collected.

Inbox

Block a subscriber

Came up directly in an earlier request this session — there's genuinely no block/unblock concept in the schema today. A real feature, not a UI toggle: needs a status, an enforcement point, and a way to reopen.

Reliability

Finish the integration-picker fix

Port the explicit-integration_id pattern (already proven twice: Calling, Broadcasting) to Sequences, and retire or fix the dead Campaigns runner — directly closes two findings above.

Platform

Admin & Reseller audit log

Who changed which package, price or role, and when. A natural fit for this hierarchy, and genuinely useful the first time a Reseller disputes a billing change.

Broadcasting

A/B send testing

Two message variants split across the audience, delivery and read rates compared — a direct extension of the Broadcasting module built this session, reusing its existing delivery tracking.

WhatsApp

Meta's native WhatsApp Flows

Distinct from this app's own visual Flow Builder — Meta's in-chat form/survey capability. Given how deep the existing WhatsApp integration already goes (Calling, Catalog, Templates), this is a real unclaimed capability, not a stretch.

Engineering

A thin test layer on the riskiest paths

Not full coverage — just login, message send, and webhook intake, the three places a silent regression would do the most damage given zero coverage exists today.

Methodology & scope. This was a static, read-only review — source inspection across both projects, npm audit run live against both lockfiles, and a handful of direct DB queries to verify hierarchy/permission claims. It is not a penetration test: I did not attempt exploitation, did not review every one of the ~90 backend route files or ~108 frontend files line by line, and did not audit the mobile/webhook payload parsing logic in depth beyond the signature-verification gap above. Treat this as a strong first pass that surfaced real, verified issues — not a guarantee that these fifteen are the only ones.
